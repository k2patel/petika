# October 31, 2026 — retained-authority identity replacement

Experimental entry collections can now rotate after their authority account enrolls
a replacement identity. Previously, changing that identity blocked further rotation.
The retained old signing key authorizes a checkpoint signed by the newly enrolled key;
the CLI requires independent confirmation of the replacement fingerprint. The server
checks the same account, increasing identity version, current enrollment, edit access,
membership generation and exact recipient roster before journal publication.

`entries rotate --replacement-identity ... --replacement-fingerprint ...` stages a
fresh root and encrypted candidate. Review and explicit submission use the new
authority bundle. Names, fields, TOTP and the delivery profile are preserved. Exact
retries retain drafts and reconcile receipts; failures do not reset client trust.
See the [workflow](../research/entry-history-transport.md#replace-the-same-accounts-authority-identity).

Local validation passed:

- Nine core checkpoint/epoch transaction tests, including both signature checks.
- Ten server epoch-journal tests, including authorization and publication failures.
- Two CLI rotation scenarios, each exercising both recovery policies, lost
  acknowledgements, cache conflicts and exact retry.
- Full-server/client-kit authority replacement recovery in Standard and experimental
  Hybrid; new identities decrypt and retired identities fail at the exact new pin.
- Default and experimental Clippy, formatting and staged secret scanning.

This closes the retained-key authority replacement item in the broader backlog.
R01–R08 remain 8/8 complete. It does not recover a lost authority signing key, delegate
authority to another account, enroll multiple device identities, or add biometric
unlock. Those capabilities remain separately tracked in the [roadmap](../roadmap.md).

This change is not deployed. Production remains on the Git settings release recorded
in [October 31 deployment evidence](../testing/deployment-2026-10-31.json). Experimental
entry-format features remain disabled by default. Remote CI results are tracked in
GitHub Actions and are separate from the local checks above.

## Draft independent-device protocol and executable model

[Draft ADR 0005](../decisions/0005-independent-device-keys.md) proposes a separate
account device authority, signed roster transitions, encryption/signing possession
checks and an explicit migration from today's shared identity. The isolated Rust
model verifies same-account independent keys, both delivery profiles, fresh-epoch
exclusion with historical access preserved, forgery/replay/conflict/rollback rejection
and re-enrollment with a separately retained authority. See
[evidence](../testing/device-key-model-2026-10-31.json). It does not implement production
account APIs, hardware enrollment, group permissions or vault migration.

The Apple probe now has a Swift package so CodeQL can discover/build it; the previous
automatic Swift-language setup failed because the standalone source had no project.
Swift package compilation and software tests pass locally. CI exercises the package
and standalone device model. Remote Swift scanning must pass before claiming that
new language is covered. The protocol remains draft pending review and exact encodings.

## Candidate device-record and roster core

Added `petika-core/experimental-device-keys`, disabled by default. The candidate core
now generates separate device/authority public records, validates bounded strict JSON,
canonical transcripts and signatures, and tracks independently pinned signed rosters.
Adjacent single-device additions/removals preserve retained keys and revocation history;
forged, stale, conflicting and structurally invalid signed updates leave the prior pin intact.

Eight targeted tests and independently regenerated Python fixtures pass. CI now checks
the candidate feature on native platforms, combined-feature Clippy and WASM compilation.
See the [candidate encoding](../device-key-format.md) and
[evidence](../testing/device-key-format-2026-10-31.json). The fixtures contain public records,
signatures and transcripts only. No production key, account data or signing credential
was added. Existing per-user identity and vault formats remain unchanged.

Enrollment challenges/proofs, API authorization/CAS, disk persistence, device packages
and migration are still pending. A valid self-signature is not encryption-key possession
or enrollment approval; independent protocol review remains required.

## Candidate enrollment proof core

The opt-in core now creates signed enrollment requests, authority-signed HPKE challenges
for both recipient keys and device-signed possession proofs. It checks explicit fingerprints,
the exact roster, expiry and both decryptions before preparing one signed successor.
Client-only pending verification state cannot be serialized and clears its expected response
after success. Preparing a successor does not advance the trusted pin before publication.

Seven enrollment tests pass, including independent Python HPKE/Ed25519 fixtures, mixed
ceremonies, missing either decryption result, re-signed corrupt packets, expiry, replay,
stale roster and intervening revocation. Existing device-format tests, combined-feature
Clippy and WASM checks remain part of validation. See the
[candidate enrollment format](../device-enrollment-format.md). Durable publication,
authenticated API transport, device packages and migration remain separate work.

The refreshed [CodeQL setup run](https://github.com/k2patel/petika/actions/runs/41240638476)
completed successfully, including Swift. The package-based Apple probe is now covered
alongside Rust, Python, JavaScript/TypeScript and Actions; this is analysis coverage,
not a statement that all pre-existing alerts have been resolved.

## Native candidate roster publication

The opt-in native `DeviceRosterJournal` now persists an independently anchored baseline,
signed adjacent transitions and operation IDs in one atomic record. Exact parent CAS
rejects competing updates; exact retries return the original receipt even after later
commits, while changed contents under the same operation ID fail. Reinitialization never
overwrites an existing or corrupt journal. Caller trust pins advance separately.

Six journal tests cover enrollment through publication/reopen, historical retry, conflicts,
receipt binding, exclusive locks/permissions, wrong anchors, corruption and write-boundary
interruptions. An old complete journal is explicitly tested against retained newer evidence;
no claim of global freshness without such evidence is made. See the
[journal contract](../device-roster-journal.md). This is a reference core primitive,
not an authenticated account API or browser persistence implementation.

## Experimental authenticated account device API

The separately gated server feature now initializes an immutable device authority with
a signature from the currently enrolled legacy identity, publishes signed additions under
own-account session/reauthentication checks, and serves adjacent history and retry receipts.
Stale source revisions, cross-account requests, competing updates, conflicting operation
IDs and attempted removal fail. An interrupted initialization resumes only its identical
empty baseline; committed corruption or missing history never triggers reinitialization.
Later legacy identity replacement cannot replace an already committed device authority.

Local validation includes independent Python bootstrap signatures/transcripts, native
account and core tests, real HTTP session/CSRF/body-limit checks, feature gates and
combined-feature linting. See the [API contract](../device-account-api.md) and
[evidence](../testing/device-account-api-2026-10-31.json).

Both a Cargo feature and runtime opt-in are required. This milestone remains local,
unpublished and undeployed. Device-session revocation, rotation/package delivery,
durable client custody/drafts and supported backup/restore are still pending. Existing
vault access and production formats are unchanged. Work is accumulated in local commits
to avoid triggering GitHub runs on every step.

## Git-authoritative synchronization direction

Updated architecture and related guides to [ADR 0006](../decisions/0006-git-authoritative-sync.md):
on-demand verified fetch before online show/edit, in-memory editing, per-entry encryption,
conditional Git publication and refresh/re-edit after a competing update. Online access requires a password plus any one authorized device key; separate
encrypted recipient packages unlock the same vault secret. Temporary
direct Git credentials depend on host capabilities, with a gateway fallback.

This is a documentation and architecture decision only. Current API/mirror behavior,
commands and deployed runtime remain unchanged. Prototype, wire-contract review, host
adapters, shared-vault authorization, device custody and explicit migration are pending.

Registration direction additionally allows local biometric/Face ID or secret-string
protection of generated device credentials, with web QR pairing approved by an existing
authority after key-possession checks. QR scanning alone grants no access. Method-selection
UI, pairing relay and platform custody/recovery remain planned implementation work.

## Mandatory per-action biometrics supersedes string unlock

The selected target now requires a fresh biometric approval for every secret action.
Earlier string-unlock alternatives in this day's registration discussion are superseded.
No cached approvals, PIN/password fallback, raw-key export, offline viewer or recovery
shortcut may bypass the trusted operation broker. Generic browser WebAuthn UV is not
sufficient evidence of biometric-only use. Platform enforcement and negative-path tests
remain unimplemented release gates. See [architecture](../architecture.md) and
[ADR 0006](../decisions/0006-git-authoritative-sync.md#mandatory-biometric-approval-for-every-secret-action).

## Experimental temporary Git-key cleanup wiring

Added configured GitHub/Gitea HTTP list/delete adapters, bounded persistent worker sweeps
and a durable session-event queue. Logout, session/client revocation and expiry, account
disablement and password changes queue cleanup before dropping affected sessions. Startup
revokes previous-process leases and a lifetime lock prevents a second cleanup worker.
Credentials stay in a protected operator file; test endpoints use synthetic local HTTP
servers. The feature/runtime gate remains off, no provider keys were changed and no
production deployment occurred. Registration, cryptographic device removal, completion
hooks and hosted validation remain pending. See [operations](../git-key-lease-cleanup.md).

## Authorized temporary Git SSH-key registration

Added candidate device-bound/SSH-key-bound challenge proofs, independent Python fixtures,
account admission checks and GitHub/Gitea create adapters. The exact public authorization
and cleanup intent are durable before remote creation. A lease makes at most one host
POST; uncertain outcomes reconcile or cancel rather than retrying creation blindly.
Completion queues that lease for cleanup. Operator owner assignment is required; write
access is off by default and host TTL limits apply. See [contract](../git-key-registration.md).

Tests use generated identities and local fake hosts only. Native SSH agent/custody,
actual-host grants and the per-secret biometric broker integration remain pending. No
production deployment, provider key mutation or automatic vault migration occurred.
