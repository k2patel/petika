# Recipient package and collection envelope formats

Package v1 uses the suite identifiers in the [OpenAPI contract](api/group-key-delivery.openapi.json).
Standard uses RFC 9180 DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, and ChaCha20Poly1305.
Hybrid uses X-Wing draft-06, KEM ID `0x647a`, with the same HPKE KDF/AEAD. Both use
single-shot base mode and an outer Ed25519 signature. No fallback between modes is allowed.

The `hpke` 0.13.0 crate implements HPKE. The hybrid adapter delegates KEM operations to
`x-wing` 0.1.1, rejects authenticated KEM mode, and derives private seeds with SHAKE256 as
specified by draft-06 §5.6. It does not implement a new KEM combiner or HPKE key schedule.

## Canonical bytes

`field(x)` is `u32be(len(x)) || x`. Text uses UTF-8; IDs and fingerprints are exactly
64 lowercase hexadecimal characters encoded as ASCII, not decoded hex. Counters are
u64 big endian, capped at 2^53−1; versions/epochs/generations start at 1.

The header, in order:

1. `field("petika:key-package:header:v1")`, u32be package version.
2. Fields: suite, deployment ID, collection ID, mode (`standard` or `hybrid-post-quantum`).
3. u64be key epoch, u64be membership generation.
4. Recipient user-ID field, u64be identity version, fingerprint field.
5. Issuer user-ID field, u64be identity version, fingerprint field.
6. Package-ID field (256 random bits represented as lowercase hex).

HPKE info is `field("petika:key-package:info:v1") || field(header)`. AAD substitutes
`petika:key-package:aad:v1`. The plaintext is a one-byte tag (1 standard, 2 hybrid)
followed by exactly 32 bytes: the data key in Standard, the X-Wing seed in Hybrid.
Ciphertext is exactly 49 bytes. Encapsulation is 32 or 1120 bytes respectively.

The Ed25519 message is `field("petika:key-package:signature:v1") || field(header) ||
field(enc) || field(ciphertext)`. Binary transport fields use canonical padded base64.
Unknown/duplicate fields, unsupported versions/suites, wrong lengths, noncanonical
base64, and records over 16 KiB are rejected. JSON order and whitespace are not signed.

Fixtures in `crates/petika-core/tests/fixtures/key-packages-v1.json` are generated by the
independent Python reference in `scripts/generate_package_vectors.py`. Rust tests compare
byte-exact headers, signatures, and decrypted payloads. Hybrid adapter tests additionally
use upstream draft-06 KATs (`xwing-draft06.json`, MIT notice alongside existing fixtures).
The generator uses Python cryptography for X25519, Ed25519, and ChaCha20Poly1305; its
reference HKDF/HPKE schedule is test-only and never linked into Petika.

## Envelope v2

Envelope v2 adds a strict `context` object with `deployment_id`, `collection_id`, and
`key_epoch`. Both recovery-wrapper and record AEAD use:

`"petika:collection:v2:" || legacy_mode_and_purpose_AAD || deployment_id_ASCII ||
collection_id_ASCII || u64be(key_epoch)`.

Legacy purpose labels remain defined in `petika-core/src/crypto.rs` and distinguish
Standard/Hybrid and wrapping/record encryption. IDs have fixed length, so concatenation
is unambiguous. Hybrid keeps its original KEM ciphertext during migration.
V1 requires no context; v2 requires valid context. Older clients reject v2. Migration
preserves keys and adds context; rotation creates a new key/seed, KEM ciphertext (hybrid),
recovery wrapper, and encrypted records at the next epoch.

Collection state schema 2 stores the snapshot, active packages, rotation generation, and
bounded transaction receipts together. Receipts hash the operation and canonical typed
request with packages sorted by package ID. Package-ID reuse is rejected within the epoch.
Journal writes precede atomic current-pointer replacement; uncommitted tails are ignored.
A successful API response follows durable pointer storage. Account locks precede collection
locks. Recovery mirrors serialize only the snapshot fields, never delivery metadata.
