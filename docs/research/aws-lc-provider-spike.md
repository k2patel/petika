# AWS-LC AES-GCM capability evidence

Date: 2026-10-18. Scope: synthetic native experiment, not production integration.
[Source and commands](../../experiments/crypto-provider/README.md).

## Reproducible build and observed results

- Host: macOS ARM64 (`aarch64-apple-darwin`); Rust 1.90.0.
- Isolated workspace: `experiments/crypto-provider`; no application dependency changes.
- Wrapper: exactly `aws-lc-rs` 1.17.0. Committed experiment lockfile pins transitive
  dependencies/checksums: `aws-lc-sys` 0.41.0 and `aws-lc-fips-sys` 0.13.17.
- Ordinary provider: build, executable round trip and three tests passed.
- FIPS-feature provider: build, executable round trip and five tests passed
  in both debug and optimized release builds;
  `try_fips_mode()` returned success. Runtime identity is `AWS-LC FIPS 3.6.0`.
  AES-GCM encryption/decryption each advanced the service indicator; a no-op did not.
  Conflicting provider feature selection is rejected.
- Tests cover successful decryption and rejection of changed ciphertext/tag, nonce,
  associated collection context, wrong key and truncated authentication data.
- Provider generates synthetic key randomness and randomized encryption nonces.
  The executable accepts no external data and prints no cryptographic material.

These checks establish basic API behavior on this host. They do not establish
independent algorithm correctness, side-channel resistance or deployment validation.
No real vault, key store, database or backup was read or changed.

## Certificate-to-build mapping

Reference: [CMVP certificate 5314](https://csrc.nist.gov/projects/cryptographic-module-validation-program/certificate/5314)
and [security policy](https://csrc.nist.gov/CSRC/media/projects/cryptographic-module-validation-program/documents/security-policies/140sp5314.pdf).
The policy is version 1.2, dated 2026-05-20. It identifies AWS-LC FIPS 3.1.0,
with `bcm.o` as the static boundary. Its listed tested environments use Amazon
Linux 2023 on Graviton4 and Intel Xeon Platinum 8375C; vendor-affirmed environments
are not listed. macOS is not one of those listed environments.

| Requirement | Evidence / remaining gap |
| --- | --- |
| Certificate status | Active when checked; recheck before release |
| Exact module provenance | Mismatch established: runtime 3.6.0 differs from certificate 5314 policy version 3.1.0; not accepted as a match |
| Installation/build compliance | Local build succeeded; section 11.1 build/configuration mapping remains open |
| Operating environment | macOS functional result only; no validated-operation claim for this host |
| Approved-service evidence | Runtime mode and individual AES-GCM seal/open indicators pass; this does not resolve certificate or environment mismatch |
| AES-GCM IV policy | Rust randomized API traced to EVP_aead_aes_256_gcm_randnonce, the policy Scenario 2 interface; production usage limits remain open |
| Key generation/import and entropy | Synthetic bytes generated by provider then imported; approved production key lifecycle not established |
| Self-tests / errors | Startup succeeded; self-test failure injection and deployed error-state behavior not tested |
| Secret lifecycle | No secret output; sample clearing is best effort, not verified zeroization |
| Browser and other native platforms | Not tested or covered by this experiment |

The wrapper's service-indicator helpers are private. The experiment now depends on
exactly the same `aws-lc-fips-sys` generated bindings to observe the native thread-local
counters around a single synchronous operation. There are no handwritten C declarations
or modified provider sources. A positive indicator is operation evidence, not certificate
proof. Version strings are likewise necessary evidence, not proof of source integrity.

## Provenance and security findings

Pinning only `aws-lc-rs = 1.17.0` did not select a certified patch release: its transitive
FIPS dependency resolved to 0.13.17, whose runtime identifies 3.6.0. The direct sys pin
now makes that diagnostic dependency explicit. Do not call this lockfile certified.

The executable supports `--expect-module 'AWS-LC FIPS 3.1.0'` and exits with status 2
before cryptographic work when this build reports 3.6.0. Matching the string would
still require source/build/environment verification. The normal diagnostic command
continues to run so newer modules can be evaluated without claiming certificate coverage.

Policy section 11.1 names the AWS-LC-FIPS-3.1.0 source archive, its SHA-256, unmodified
source requirements and build procedure. A future matching candidate must verify that
archive, build recipe, static boundary and environment; Cargo checksums alone are not
that mapping. No older module is installed just to make the string check pass.

Upstream advisory [GHSA-q87m-xr7j-vrww](https://github.com/aws/aws-lc/security/advisories/GHSA-q87m-xr7j-vrww)
includes FIPS versions from 3.0.0 before 3.3.0 and fixes CRL certificate-validation
behavior in 3.3.0. This is not an AES-GCM break and this experiment performs no X.509
validation. It nevertheless requires a scoped vulnerability assessment before choosing
3.1.0 for a broader application. Certificate matching must not replace patch assessment.

The [upstream releases](https://github.com/aws/aws-lc-rs/releases) also provide newer
wrapper APIs for version inspection. A future wrapper upgrade must preserve the
explicit module mapping and rerun this evidence; do not infer approval from a major
FIPS branch or upgrade dependencies without reviewing the resolved module.
